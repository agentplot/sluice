# sluice rules

The rules that bind wherever a change is made in this repository,
written so a reviewer can point at a diff and say which rule it breaks.
The narrative is the statement in agentplot/blueprints,
`design/sluice/requirements.md`; a rule here names the clause it
enforces and never restates it. There are no area pages yet; a rule
that binds only one part of the tree moves to an area page when that
part exists.

## Rules

### The core and its seams

- **[core.1]** Code outside a profile names no task runner, worktree tool, multiplexer, service manager or forge.
- **[core.2]** Every seam of Part B is reached through exactly one interface, and a profile implements that interface and nothing of the core.
- **[core.3]** A seam with a single profile has an ADR saying why one is enough.

### Branches and landings

- **[core.4]** No code path reachable from the submit operation writes a branch's ref; a round of sluice's work may be run by any process, a waiting driver included.
- **[core.5]** A branch is moved only with the expected old revision, and a move whose expectation fails is reported, never retried blind.
- **[core.6]** A candidate is formed from the branch's revision and the entries ahead of it, in order, and from nothing else.
- **[core.17]** A candidate whose entries ahead land exactly as they were tested is the same candidate on the revision they land as: its tree, its runs and its verdict stand, and it is named as that revision extended by the entries still ahead of it.
- **[core.39]** A submission whose work no required check reads, by the check's affected reading at the branch's current revision and at each candidate formed and not landed, as it would land now, and which merges cleanly onto them and onto the work of every entry ahead, lands at the first round that reads it, beside the chain and with nothing run; a candidate formed before it keeps its runs and verdict and lands from the revision it made, carrying its work, never formed or tested again for it; and its landing commit names as its verdict its own, passed with nothing run, with the verdict that covers the revision it landed on and the revision that verdict landed as, which the branch's records name, or the work takes the chain.
- **[core.43]** A landing commit and a request sluice opens name what lands, the submit's subject or the submitted branch where it gave none, never a commit's message; a form the policy gives the landing line takes the subject in its slot for the work; and a request's description carries its commits' messages whole, as many as the forge's limit holds.
- **[core.48]** A submission whose work its branch already holds is landed as the commit that landed it, and is never formed, run, landed again or withdrawn; a wait reports its own submission's end and never another's as its own: landed, as the commit that landed it, once its branch holds its head, whatever landing took it, its branch read as a round reads it, following meanwhile the later submission or open request that carries its work; and withdrawn only where no work of it goes on or what carried it stopped short, naming what carried it; and where no files are checked out, a delivery read takes as its own what a worktree on the branch its `HEAD` names would, reading neither the folder's files nor its `HEAD`'s commit, and never fails, or leaves an outcome pending, because no files are checked out.
- **[core.50]** A submission that names a branch sluice lands on as its head is that branch's work and records no worktree and no session as its submitter; its outcome records no delivery and is owed to no reader, and a status gives it in an inbox's words; and a worktree takes as its own only what it submitted, and a pull request's only from a branch sluice lands on nowhere.
- **[core.52]** A submission's outcome is owed and done only by weir's delivery form, through `weir-delivery`'s calls over the branch's own store, which passes weir's pack: one delivery under `<id>:<outcome>`, its reader the submission's work, owed until that reader confirms it naming its key; no hand-over confirms it but in the call that says its reader confirms on receipt, an owed outcome past its span is shown expired with its reader wherever sluice shows what is owed, and nothing but a done delivery leaves the store.
- **[core.27]** Which remote a branch is on is read from the policy at every revision of the branch the host holds, its own ref and each remote's tracking ref, never from the host's own ref alone and never by a fetch, and from each revision only as far as that reading needs, the remote named for the branch and whether signers are named, so a revision this sluice refuses elsewhere in its policy decides the remote all the same.
- **[core.28]** A read of a remote the core could not make is logged on the branch with the remote's own words, once per distinct cause and host, with its end, and is never reported only to the process that met it.
- **[core.47]** A write the protection refused is logged on the branch once per distinct cause and host, a cause being its command whatever full revisions it names, with its end; its count, first and last are kept in the branch's live records and shown from them by the overview and a branch's status until a day passes with none, never counted from the log, and a tool that watches the host reads them there.
- **[core.29]** Every call to a remote runs under sluice's one retry policy, a maintained crate's backoff bounded by its caller, which tries again what the remote never judged, a credential it refused bought afresh for the next try, never what the remote answered, and never a push or a forge write whose answer was not read, which is settled by reading the branch or the forge, a write nothing reads back reported unanswered; and a forge's word that an allowance is spent is a pause until the time it names, kept in the host's state and honoured by every process on the host, which a command waits out within its own limit and a round passes by.
- **[core.31]** Nothing of sluice's need run between its commands for any guarantee to hold, and no policy, configuration or document of sluice's tells a host to run a daemon, a machine running one only by keeping `sluice daemon` running by its own choice, and sluice working with none (Record 0093 as amended 2026-11-08, accepted by the user that day.); nothing is installed for sluice: a command that needs the host's queues moved reaches sluice's one host process for its user or starts it, which holds every repository's queues apart and the host's bound on runs, and ends once no queue has work in play and nothing follows it; a wait or a watch follows it and runs no round; a submission's outcome is pushed into its submitter's session as a notice, each hand-over of it recorded by sluice alone, on the word of the carrier that made it and never on a notify that handed nothing, no carrier keeping a list of its own of what it handed over; and a session that starts collects every outcome owed to its readers by `sluice inbox`, so no wait need stand for an outcome to arrive (core.52); and a reader's tick asks the forge nothing but what the discovery due or a move on the host calls for.

### Forge reads

- **[core.32]** sluice asks the forge only what could have moved: the open requests at the deployment's interval or after a move on the host, every read conditional on the answer the host keeps for its address, a request's reviews, checks, ready marks and comments only once it or its entry moved or while it waits on its conditions, a draft by the list alone, one query per branch where the forge answers one, and its own check and report posted only when what they say changes.
- **[core.42]** What sluice reads of one request, or cannot, decides that request alone: a request whose head or conditions it cannot read, draft or ready, is reported by name, read again each round and holds no other; a draft whose head cannot be read is a draft with no forecast, holding nothing.
- **[core.33]** A branch's requests are taken in only by whatever executes its queue, in one of four ways the machines choose and no policy names, the submitting machine's own sluice process with no daemon, a daemon on that machine, a daemon on another or GitHub Actions' jobs, which also tests and lands them, and only by an executor whose signature the branch accepts, never by two ways, two machines or two copies, and never by one that does only part of that (Record 0093 as amended 2026-11-08, accepted by the user that day.); a host that does not execute the branch's queue takes nothing in, a host's submit opens or updates its request and marks it ready, and the host follows the request on the forge and by what sluice's check on its head says, which carries the request's entry as fields, never by the conclusion the forge kept.

### Verdicts and attribution

- **[core.7]** Every check run is recorded with its key, outcome and executor before any verdict is read from it, a fail exactly as a pass.
- **[core.8]** A failure is attributed to one entry, and only after every candidate ahead of it has a verdict.
- **[core.9]** A replay is recorded as a replay, never as a run.
- **[core.22]** A result counts for a gate only through a signer the branch's policy names and a claim that signer may make, never through what a record says of its executor alone; on a branch in one host's own files, through the runs that host's sluice starts.
- **[core.40]** Every record a signer signs is of the kind in-toto's catalogue gives what it says, a run's a Test Result; sluice defines its own kind only for what no catalogued kind carries, a set-aside.
- **[core.34]** A check's results are weighed together only under one grant: a key's outcomes for a flake, and the pass that proves a replay, are read only from results whose executor gave the run's own grant, on every branch, signed or not, and a result recorded with no grant only with others that have none.
- **[core.35]** A check that did not pass in a run whose executor reports refusing the run something has no outcome; the refusal is read from the executor's own report, never from what a check printed or how it failed, and a check that passed keeps its pass, unless the run kept nothing that proves it ran, when it has none and nobody is blamed (record 0105).
- **[core.37]** sluice runs no readiness command the repository writes, before a run or after one: a run has no outcome only on the executor's own report of a refusal, the check's own not-run exit, or the executor's own finding after a run in which a check did not pass that a requirement the policy asks has left the host, never on a probe sluice or the repository runs.
- **[core.38]** A run whose policy asks for a container engine is claimed only by an executor that finds one the run can reach; one that finds none refuses the run before claiming it and leaves it open for a host that can; after a run in which a check did not pass the executor looks at the engine again, and where it has gone the run has no outcome, nobody is blamed and a pass stands; a requirement is read from the host only where the executor can see it for itself and a check cannot bring it up. On a host whose system Nix manages, a run during which the active system's revision moved, between the executor's reading as the run began and its reading after a check did not pass, has no outcome, nobody is blamed and a pass stands, and it runs again only in a place made afresh; on any other host nothing is read and runs are read as before (record 0097).

### Places

- **[core.10]** The core starts no service; the checks it runs are one process group, ended with their place or their time limit, and what they hand to another process is removed when their place is released.
- **[core.11]** Every record a reader may need is readable with no sluice process running, from every host that submits to its branch.
- **[core.14]** Nothing the core decides is held between steps outside the records, and no two steps act on one branch at once.
- **[core.41]** A finished submission leaves the live records unchanged in form, an index line naming it and its times; a round, the overview, a branch's status and a wait read the live records and the index alone; and the log is kept in parts, none of its lines changed once written.
- **[core.15]** A branch's gate is read from the branch's current revision, never from a candidate or a place.
- **[core.16]** The core releases only places it made, and a session's only when its working copy is gone; otherwise a session's place is released only by `sluice release` at its session's or driver's asking, and a preview only by `sluice release` at its caller's asking or when its command failed or its checkout is gone.
- **[core.18]** A session run counts toward the bound from the host's state and is recorded under its keys only when its worktree holds exactly its head.
- **[core.49]** A run counts toward the host's bound from the count that chose it, its part held by sluice's host process through its start (record 0093) and given back at once when the start fails; and where a candidate's run and a session's or a preview's wait for room at once, the candidate's starts first, until one has started in room a waiting session's run could take, when the next such room is a session's, sessions' and previews' runs starting in the order they came to wait.
- **[core.19]** A preview is made only at a revision its branch has landed, and decides nothing: its command is never recorded as a run, read by a gate, or waited on by a submission.
- **[core.20]** The core writes no working copy it neither made nor adopted: a worktree that has checked out a branch sluice lands on is reported, never moved, and never stops a landing.
- **[core.23]** An instance claims no run while a place it made belongs to a candidate with a verdict, an obsolete one, or a claim it no longer holds, until each such place is released or held.
- **[core.30]** A place's scratch is under a short directory of the host user's own, apart from every repository, at a path that grows with neither the place's name, its checkout's location nor the repository's, and the place's record names it.
- **[core.46]** Every working copy sluice runs a check or a command in, and one its caller asks `sluice equip` of, is equipped by one sequence of the check profile's: the toolchain the policy names, then the runner's install of what the working copy pins, its version check and its setup, each outside the executor with a run's environment, stopping at the first that fails; one sluice only reads in is equipped up to its version check; and an equip adopts and keeps nothing.

### Design and records

- **[core.12]** A change that bears on a clause cites the clause by number; a clause that no longer holds is changed in the statement first, never worked around here.
- **[core.13]** Nothing commercial, no pricing, tier or customer, appears in this repository.
- **[core.26]** The site, the README, the plugins' skills and the commands' output speak to any host's operator: no word the statement coined that the reader cannot see in the product, no machine, fleet, partition, deployment or tool of ours, and no team's branch scheme as sluice's own; a skill that proposes a branch or a pattern follows the project's own naming.
- **[core.25]** On a host, at most one process reads a repository's records to watch its queues; every other watch and wait follows that reader's document.

### Setting up

- **[core.44]** Setup moves nothing a process outside its session has open, and goes on in a repository's one working copy only on the operator's word, which its record says; once set up, no command warns of the layout.
- **[core.45]** A branch whose team lands by pull request keeps its way whole and sluice alone lands it: no way of sluice's in which the host's merge button, a merge queue of the host's or a merge by hand lands and sluice only tests; and setup asks whether the team lands by pull request today and, where it does, writes the branch's conditions.
- **[core.51]** The flake's module writes the host's own settings alone, `~/.config/sluice/config.toml`, from options named as the file names them, a key left unset left out of the file; it names a key only by a path outside the Nix store, writes no other tool's file, and installs nothing for sluice to run.
- **[core.53]** sluice's telemetry is the host's own setting, `[telemetry]`, a command's own flag or sluice's own variable choosing for that command alone; OpenTelemetry's variables only turn telemetry or a signal off, or name the collector where the table names none; and a run's checks are handed the collector and signals sluice sends, none of the caller's where the table names a collector. (Record 0106.)
- **[core.54]** A sluice process that outlives a command takes up the host's own settings afresh once their file changes, between rounds and never within one, so a change takes effect from its next round with nothing on the host restarting it; a run keeps the settings it started under. (Record 0107.)
- **[core.57]** herdr's configuration file is the person's, and nothing of sluice's writes it but the person's agent at their asking: the herdr plugin's setup shows its lines, and the setup skill merges them into the file as the person keeps it, on keys neither the file nor herdr binds, shows them instead where a tool writes the file, and puts back a write that fails `herdr config check`.

### The gate

- **[core.21]** Every file the tree tracks, Markdown aside, is owned by a formatter the gate runs, or is excluded by name with its reason; no task reads a Markdown file to format, lint, test or check it (agentplot/blueprints principle 16); every language with a linter is linted; every directory under `plugins/`, `site/` and the flake's `nix/` is a moon project of its own, listed in `.moon/workspace.yml` with its language declared, whose check-fast tasks validate, type-check and test it, one task per check.
- **[core.24]** Every tool a gate task runs is the version the tree pins, on every host that runs the gate, so CI and `sluice exec` hold a tree to the same rules.

### Releases

- **[core.55]** A release's tag names a release commit cut from the pushed commit off main, which writes the release's version into every file that carries sluice's version; main's tree names `0.0.0`, nothing of a release is committed to main, and a build takes sluice's version from its tree alone, given none by its builder.

## Details

- **core.1** Rules out: the strings `moon`, `wt`, `worktrunk`, `devenv`, `herdr`, `gh`, `crew`, `boomdrive` in any module outside a profile directory; an import of a profile from the core. - **core.3** Rules out: a seam whose only profile is undocumented as such. Source: ADR 0003.
- **core.4** Rules out: `update-ref`, `push`, a merge or a fast-forward in the submit operation or anything it calls; a round that behaves differently because a driver ran it; a submit pushing, or writing the host's copy of, a branch sluice lands on (124).
