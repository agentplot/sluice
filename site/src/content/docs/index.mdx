## Get started

In a Claude Code session in a terminal, install the plugin, then ask Claude
to set sluice up in your repository. It installs the `sluice` binary too,
asking first.

```
/plugin marketplace add agentplot/sluice
/plugin install sluice@sluice
```

## Why

Run ten coding agents in ten worktrees and each one's tests pass on its
own. Merge them and the branch breaks, because nobody tested the
combination. Let the agents merge for themselves and they race, rebase
over each other's work, and can't tell whose change broke the build.

sluice takes merging away from the agents. Each one finishes its work and
**submits** it. sluice queues the submissions, tests each one **on top of
everything queued ahead of it**, and lands it only if that exact
combination passes.

<Flow>
  <Step kind="submit" title="Submit">
    An agent finishes its work in its own worktree and submits it to a
    branch. The submission joins that branch's queue. No agent merges.
  </Step>
  <Step kind="combine" title="Combine">
    Each submission is tested on top of everything queued ahead of it:
    the branch, plus every submission ahead, plus this one, checked out
    fresh in its own worktree. Several combinations run at once.
  </Step>
  <Step kind="test" title="Blame one">
    When a combination fails, sluice waits for a result on every
    combination ahead, works out the one submission at fault and tells
    only that agent, with the failing tests and their logs. The rest
    are formed again without it, and the tests that already passed are
    replayed, not run.
  </Step>
  <Step kind="land" title="Land">
    A combination that passes lands as a merge commit carrying exactly
    the tree that passed. A git hook refuses every other update to the
    branch, and sluice moves it only from the revision it tested on.
  </Step>
</Flow>

<CardGrid>
  <Card title="Try what landed" icon="laptop">
    `sluice preview` brings a revision the branch landed up on your
    repository's own stack, at addresses a person opens, and keeps it
    until it is released. One per landing, side by side, nothing kept
    checked out by hand. [Previews](/sluice/guides/previews/).
  </Card>
  <Card title="No daemon" icon="setting">
    sluice keeps nothing running itself. A waiting `sluice submit` drives
    the queue while it waits; `sluice run`, or `sluice step` from cron,

    keep until it is released. Every decision is written to plain files
    before it is acted on, so a crash at any point resumes from the files.
  </Card>
</CardGrid>

## Part of the Flywheel family

sluice is the family's landing step. headwater and eddy notice what
changed, millpond keeps the inbox, flume launches the work in a worktree
and sounding works a question through; sluice lands what they make. Each
tool stands alone, and sluice is the one in use today.

## Install by hand

```sh
nix profile install github:agentplot/sluice
```

Other ways: a release binary for macOS on Apple silicon and Linux on
x86-64 and ARM, `cargo install --locked --git https://github.com/agentplot/sluice sluice`
with Rust 1.98 or later, or the flake as an input. Each installs two
executables: `sluice`, and `wt-submit`, which
[worktrunk](https://github.com/max-sixty/worktrunk) runs as `wt submit`.

```sh
curl -fsSL https://github.com/agentplot/sluice/releases/latest/download/sluice-aarch64-darwin.tar.gz \
  | tar -xz -C ~/.local/bin sluice wt-submit
```

## Quick start

**1. Say what gates the branch.** Commit `.config/sluice.toml`:

```toml
[tests]
runner = "command"          # or "moon", to run only what a change affects
command = "make test"

[branches.main]
parallel = 4                # combinations under test at once
```

sluice reads this file from the branch itself, never from a submission,
so no submission can loosen the rules that judge it.

**2. Protect the branch**, once per repository:

```sh
sluice protect
```

**3. Submit** from an agent's worktree, with its work committed:

```sh
sluice submit main          # or: wt submit main
```

It waits, and says what happened:

```
submission 3 to main · 1 queued ahead (#2)
testing main + #2 + #3 · 4 tasks to run, 2 replayed
passed · landed as 9f2c1e4
```

or, when this submission broke the combination:

```
failed: tests:t-cards
  on main + #2 + #3 (5b81d07)
  #2 passed on its own, so the failure is from this submission
  log of tests:t-cards: /…/sluice/.logs/main/c4/tests:t-cards.log
the agent working in unit/cards fixes it there and submits again
```

The exit code says the same:

| exit | meaning |
|---|---|
| `0` | landed |
| `1` | failed |
| `2` | a conflict or a refusal |
| `130` | stopped with Ctrl-C; the submission stays queued |

A complete setup, with moon, a sandbox, a build cache and two tiers of
branches, is the [walkthrough](/sluice/guides/walkthrough/). The whole
configuration is in the [reference](/sluice/reference/configuration/).
