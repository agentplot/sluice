## 2. The compile-cache step

- [ ] 2.1 Add `crates/sluice/src/compile_cache.rs` and a hidden `sluice compile-cache (--host | --own <dir>) -- <command…>` beside `Supervise` in `crates/sluice/src/lib.rs` and `main.rs` (design D3). It finds `sccache` on `PATH`, checks the incremental variables, then runs the command with `RUSTC_WRAPPER`, `SCCACHE_NO_DAEMON=1`, `SCCACHE_CLIENT_SIDE=1` and the server's address (design D6). Each fallback writes one line to stderr saying why and runs the command with no `RUSTC_WRAPPER` from sluice. The step passes the command's exit code through, and re-raises a signal that ended it. Module docs say the module is the check profile's and names the tool (core.1). Verify with unit tests in the module for the fallbacks' order and the socket path's length rule (`cli:test`).
- [ ] 2.2 Implement `--own <dir>` (design D4): take `<dir>/lock` with `File::try_lock`; choose the socket under `$SLUICE_TMP`, or in `<dir>` past 104 bytes; start the server in the foreground with `SCCACHE_START_SERVER=1`, `SCCACHE_NO_DAEMON=1`, `SCCACHE_DIR`, `SCCACHE_SERVER_UDS` and `SCCACHE_IDLE_TIMEOUT=0`, its output to `$SLUICE_TMP/compile-cache.log`; wait up to ten seconds for the socket; run the command; then end the server. Verify with unit tests: a held lock falls back without starting anything, and a server that never listens is ended and falls back. Use a fake `sccache` script on `PATH` in a temporary directory (`cli:test`).
- [ ] 2.3 Implement `--host` (design D5): take the address from `SCCACHE_SERVER_UDS`, else `SCCACHE_SERVER_PORT`, else 127.0.0.1:4226; connect once; `exec` the command addressed to it, or fall back saying the host's compile server did not answer. Verify with unit tests against a listening and a closed Unix socket in a temporary directory (`cli:test`).
